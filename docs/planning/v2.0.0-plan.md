# v2.0.0 plan — POST retry, response capture, body transformation

Branch: `release/2.0.0`. Tag will be `v2.0.0`.

## Why a major

This started as an additive minor. Two things made it a major instead:

1. `Gateway:RequestLimits` split into one budget per physical resource
   (`MaxRamBufferedBodyBytes` / `MaxDiskBufferedBodyBytes`), replacing the combined RAM+disk total.
   The removed keys are rejected at startup rather than ignored.
2. `BodyCapturePlugin` was removed, folded into the streaming capture plugin, which now picks
   reuse-vs-tee per request.

See the CHANGELOG for the upgrade table.

`96d1677`, already on the branch, argues the same way: an absent `maxSize` changed from "capture the
whole body" to "capture 4 KiB". Every shipped route config sets `maxSize`, so nothing observable
changes, but by strict reading that is a behaviour change rather than a fix.

`Directory.Build.props` reads `2.0.0`.

## 0. Prerequisite — make the capture budget apply on both paths

**Everything else in this plan depends on this.** Ship it first.

`IPipelinePlugin.CaptureMemoryBytes` is summed once at chain-compile time, then applied *only* in
the streaming branch of `BuildRouteChain`. The buffering branch calls
`BufferRequestBody(route, gatewayOptions, readsBody)` and never sees `captureBytes`. A capture
plugin on a route that also carries a body-reading plugin, or a retry policy, has its declaration
silently discarded — the exact "per-request cap × unknown concurrency, nothing sheds" shape we
rejected when comparing against Envoy's tap filter.

**Change**: hoist the reserve/release out of the streaming lambda into one `chain.Use` placed
*before* the branch, so both paths inherit it.

```csharp
// before the if/else in BuildRouteChain
if (captureBytes > 0)
{
    chain.Use(async (context, next) =>
    {
        var budget = context.RequestServices.GetRequiredService<Middleware.RequestBodyBudget>();
        if (!budget.TryReserve(captureBytes)) { /* 503 */ return; }
        try { await next(context); } finally { budget.Release(captureBytes); }
    });
}
```

Also update the `CaptureMemoryBytes` doc comment — it currently says "Exists for plugins that
capture on the streaming path", which stops being true here.

**Test**: the mirror of `CaptureMemoryBudgetTests` with a body-reading plugin also on the route, so
the chain takes the buffered branch. It passes today by *not* shedding; after the fix it must 503.

## 1. Allow retry on POST

Opt-in per route, default off. This is opting out of a property that is currently asserted by a
test, described in five docs, and measured by a benchmark — not patching an oversight.

**Config**: `"retry": { "maxAttempts": 3, "retryNonIdempotent": true }`

**Two call sites must agree**, and missing either produces a silent bug:

1. [`UpstreamRetry.InvokeAsync:92`](../../src/ConduitSharp.Gateway.AspNetCore/Proxy/UpstreamRetry.cs#L92)
   — the gate currently tests the method *before* looking up the route's retry config. The lookup
   has to move first, since the flag lives in that config.
2. [`GatewayApplicationBuilderExtensions:417`](../../src/ConduitSharp.Gateway.AspNetCore/GatewayApplicationBuilderExtensions.cs#L417)
   — `if (!readsBody && !IsIdempotent(method))` streams the body. A POST that may now be replayed
   **must** buffer, or the retry loop has nothing to rewind. This is the one that fails silently:
   retry appears configured, the second attempt sends an empty body.

**Validation**: `retryNonIdempotent` with `streamOnly` is already rejected via the existing
retry/streamOnly rule, since it requires `maxAttempts > 1`.

**Tests**
- POST + flag on → replayed, full body intact on attempt 2 (mirror `IdempotentMethodWithBody_RetryResendsFullBody`)
- POST + flag on → route takes the buffered path, so 413/503 limits engage
- `NonIdempotentMethod_IsNotRetried_EvenWhenConfigured` stays green untouched — it is the
  default-behaviour regression guard

**Docs**: `ROUTING.md:121`, `AGENTDOC.md:335` + `:427`, `GATEWAY_SETTINGS.md:46`,
`ARCHITECTURE.md:250` all state "idempotent methods only". Each needs the opt-in and its risk:
a POST may already have been applied upstream, so a replay can double-apply it.

**Benchmarks**: s1's premise ("POST is method-aware, no buffer") stays true by default. No bench
changes. Worth adding a note in `run.sh` that the measured saving is now a default, not a law.

## 2. Response body capture, budgeted

Depends on §0.

### 2a. To OTLP — two lines

`StreamingBodyCapturePlugin` already hosts the framework's HttpLogging middleware, whose
`ResponseBufferingStream` is a bounded pooled tee equivalent to Envoy's tap filter.

- `options.LoggingFields = HttpLoggingFields.RequestBody | HttpLoggingFields.ResponseBody`
- set `logging.ResponseBodyLogLimit` in `OnResponseAsync`
- `CaptureMemoryBytes` → `2 * MaxSize(config)`: two prefixes are held per request now, and the
  honesty of that number is the whole safety mechanism
- the comment on `OnResponseAsync` ("Request bodies only — the response never enters the picture")
  becomes false

### 2b. To file — new variant, shared sink

`BodyCaptureToFilePlugin`'s sink is direction-agnostic: `(time, path, traceId, buffer, length,
truncated)` → bounded channel → `Utf8JsonWriter` → append → roll. Reuse it whole, including the
`DropWrite` + return-in-`finally` pooled-buffer discipline.

Only the front half is new: wrap `Response.Body` in a bounded write-through tee, enqueue after
`next` returns. ~40 lines.

**This cannot be a config flag on the existing plugin.** `ReadsRequestBody` is a property on the
plugin, not a function of route config, and plugins are singletons — so a combined plugin would
have to declare `true` always, forcing request buffering on response-only routes. As a separate
variant it declares `false`, stays on the streaming path, and (after §0) is budgeted either way.

Justification over 2a is measured, not theoretical: at c=256 the file sink held 100% of records
while in-process OTLP dropped 20–25%. Response bodies are larger than request bodies, so that gap
widens.

### 2c. Ordering

**Chain model (decided): Envoy's single reverse-unwind chain, not Kong/APISIX phases.** One ordered
`plugins[]`, forward terminal; response-phase work runs after `next()` in reverse `order`. No second
array, no phase enum. All §2/§3 response plugins are built this way — see *Request and response
phases* in `docs/AGENTDOC.md`.

Order capture **before** `cache` in the chain. `CachePlugin` returns on a HIT before it swaps
`Response.Body`, so `ServeAsync` writes into the capture wrapper and hits are recorded. Ordered
after cache, every HIT is invisible. That "before" is a lower `order` value — capture's swap is
outermost, so it wraps the cache and sees a HIT's bytes. Document it; do not leave it to discovery.

## 3. Body transformation, budgeted

Depends on §0. Materially harder than §2 — mutation is a different cost class from capture.

### Why response transform cannot be a tee

You cannot rewrite a prefix; you need the whole body before emitting any of it. That means
**hold-back**, not write-through, which forces four things capture never needed:

1. **`Content-Length` is invalidated.** Set the new length before the response starts, or drop it
   and let chunked take over. Silent truncation otherwise.
2. **Headers are one-shot.** Once `HasStarted` flips they are on the wire. Envoy states the same
   constraint from the other side: header mutations only apply in `BUFFERED` mode.
3. **Unbounded memory.** This is the budget question below.
4. **SSE is structurally incompatible.** Hold-back destroys streaming. Detect `text/event-stream`
   and unknown-length responses and pass through untransformed. APISIX has open bugs here
   (#11977, #12665) — this is not hypothetical.

Plus: if upstream returns gzip, the transform sees compressed bytes. Strip `Accept-Encoding` on the
forward, or decompress.

### The budget

`RequestBodyBudget` is internal, so it can be reused and renamed. Reuse it rather than adding a
second ceiling — one number to tune, one 503 to reason about. Suggest renaming to
`BodyBufferBudget`, since it stops being request-only.

Reserve `maxTransformBytes` (the cap, not the actual size — the response size is unknown up front)
*before* calling `next`, release in `finally`. Reserving before `next` means the response has not
started, so a refusal can still be a clean 503.

Request-side transform is cheaper: the request body is already buffered and budgeted, so only the
*output* copy needs declaring.

### Overflow is a security decision, not a tuning one

Response exceeds `maxTransformBytes` mid-stream. Two options, and the default matters:

- `"onOverflow": "fail"` → 502. **Default.**
- `"onOverflow": "passthrough"` → emit untransformed.

For the use case that justifies this feature at all — redaction — passthrough leaks exactly the
thing the transform existed to scrub. Fail closed.

### Scope

Ship the mechanism plus one transform, not a template engine. Redaction (regex or JSON-path field
scrub) is the transform worth having in a gateway. Explicitly **not** doing cross-provider schema
translation (OpenAI ↔ Anthropic ↔ Bedrock): most providers ship OpenAI-compatible endpoints, so
standardise there and translate only when forced.

### Cheaper sibling worth doing first

Response **header** transformation needs none of the above:

```csharp
context.Response.OnStarting(() => { /* add / set / remove */ return Task.CompletedTask; });
await next(context);
```

No buffering, SSE-safe, ~15 lines as a `direction` option on the existing `HeaderTransformPlugin`,
which today only touches `Request.Headers`. Highest ratio in this document. Do it regardless of
whether §3 ships.
